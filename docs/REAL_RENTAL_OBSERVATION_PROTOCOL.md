# RIVO — Real Rental Observation Protocol
## Quality Classification Rules for Data Collectors

**Phase 11 | Team CLAIRES | ST1010 | PS-11-S3 | Chennai Pilot**

---

## Purpose

This document defines exactly what makes an observation VALID,
QUESTIONABLE, or REJECTED. Every team member collecting data
must follow these rules consistently.

A RIVO observation is a point-in-time price fact for a specific
real property. It is NOT a listing advertisement. It is NOT a
model estimate. It is NOT an interview note.

---

## Three Classification States

### ✅ VALID

The observation passes all hard checks and has adequate location precision.

**Criteria (all must be true):**
- `is_synthetic = false`
- `is_demo = false`
- `source` is named and genuinely independent
- `observed_at` is a real timestamp (not guessed, not invented)
- `rent_monthly` is > ₹2,000 and ≤ ₹10,00,000
- `bhk` is between 0 and 10
- Coordinates are within Chennai pilot bounds (lat 12.75–13.35, lon 80.00–80.35)
- `geocode_confidence` is HIGH or MEDIUM

**Examples:**

| What happened | Classification |
|---|---|
| Owner confirms ₹18,000/mo for 2BHK flat in Velachery, location pin dropped on map | ✅ VALID |
| Rent board photographed: "2 BHK ₹20,000", Google Maps pin confirmed by field agent | ✅ VALID |
| Authorized portal API returns confirmed current listing in Anna Nagar | ✅ VALID |
| Tenant interview: "We pay ₹15,500/mo for 1BHK in T. Nagar since April 2025" | ✅ VALID |

---

### ⚠️ QUESTIONABLE

The rent and source are real, but location precision is weak.

**Criteria (passes hard checks, but one or more soft issues):**
- Coordinates are missing or only at locality centroid
- `geocode_confidence = LOW`
- Address is vague ("somewhere in Adyar")

**Action:** Still accepted into the system. Still `eligible_for_model`.
However, it contributes lower weight to spatial surface estimation.

**Examples:**

| What happened | Classification |
|---|---|
| Owner confirmed rent but refused to give address; only locality known | ⚠️ QUESTIONABLE |
| Rent board seen from a moving vehicle; locality confirmed, exact street not | ⚠️ QUESTIONABLE |
| Listing aggregator gives locality-only; no street address | ⚠️ QUESTIONABLE |

---

### ❌ REJECTED

The observation fails a hard check. It is NEVER accepted.

**Rejection reasons:**

| Reason | Example |
|---|---|
| `is_synthetic = true` | Row generated by a script |
| `is_demo = true` | Demo seed listing |
| Missing `source` | No provenance recorded |
| Missing `observed_at` | Timestamp not recorded |
| `rent_monthly ≤ 0` | Negative or zero rent |
| `rent_monthly < ₹2,000` | Below plausible minimum |
| `rent_monthly > ₹10,00,000` | Likely data entry error |
| `bhk` outside 0–10 | Data entry error |
| Coordinates outside Chennai | Wrong city or data error |
| `is_demo = true` from CMRL seed listings | Demo data |
| Observations converted from demo seed | Fabrication |

**Rejected observations are never stored in the eligible pool.**
They are logged with rejection reason for audit purposes.

## Duplicate Handling

**Same observation event:** If you record the same property on the same day
with the same rent, the dataset preparation step will deduplicate it.
This is fine — the deduplication is auditable.

**Different observation events:** If the rent changes, or you're recording
at a different time (e.g., rent rose from ₹18,000 to ₹19,500 next month),
record a new observation. Do NOT update the old one.

Example:

```
PROP-VEL-001  |  2025-09-01  |  ₹18,000  |  AVAILABLE  → Observation 1
PROP-VEL-001  |  2025-10-01  |  ₹19,500  |  AVAILABLE  → Observation 2
```

This is 1 property with 2 observations. Both are kept. This is correct.

## Availability Classification

Use these states correctly:

| State | When to use |
|---|---|
| `AVAILABLE` | Owner/agent confirms it's available right now |
| `PENDING_CONFIRMATION` | Seen advertised but not confirmed with owner |
| `RECENTLY_SEEN` | Was available 2–4 weeks ago; current status unknown |
| `UNAVAILABLE` | Confirmed taken or withdrawn |
| `UNKNOWN` | No information on current availability |

**Do NOT promote `RECENTLY_SEEN` to `AVAILABLE` without fresh confirmation.**

---

## Verification Classification

| Status | Meaning |
|---|---|
| `UNVERIFIED` | Observation recorded; source not independently checked |
| `LOCATION_VERIFIED` | Coordinates confirmed at property site by RIVO agent |
| `OWNER_ATTESTED` | Owner or authorized agent explicitly confirmed the rent |
| `RIVO_VERIFIED` | RIVO has independently confirmed via in-person visit |

**LIVE freshness does NOT mean RIVO_VERIFIED.**
A listing can be LIVE + UNVERIFIED (owner submitted without RIVO check).
These are separate axes.

---

## Geocode Confidence

| Level | Meaning | How to achieve |
|---|---|---|
| `HIGH` | Coordinates within 10m of property entrance | GPS pin from map app at property; owner shares Google Maps link |
| `MEDIUM` | Coordinates within ~100m | Street-level geocoding from address string; nearby landmark |
| `LOW` | Coordinates at locality centroid only | Only locality name known; no street address |

---

## Source Diversity Rules

Two observations count as having **2 independent sources** ONLY when:
- They come from genuinely different collection channels
- The channels are not controlled by the same person/system

Examples of what counts as 2 sources:
- `field_agent` + `owner_interview` ✅
- `rivo_direct` + `authorized_portal_api_2025` ✅

Examples of what does NOT count as 2 sources:
- `field_agent_morning` + `field_agent_evening` ❌ (same collector, same method)
- `owner_interview_v1` + `owner_interview_v2` ❌ (same channel, different label)
- `demo_seed` + any other demo label ❌ (both are demo)

---

## Property Counting Rules

**1 property = 1 unique `listing_id`**

Multiple observations of the SAME property do NOT create multiple properties:

```
PROP-001  ₹18,000  2025-09-01  → observation
PROP-001  ₹18,500  2025-10-01  → observation
```
= 1 property, 2 observations ✅

Two different flats in the same building on the same street:

```
PROP-001  2BHK  ₹18,000  Floor 2
PROP-002  2BHK  ₹17,500  Floor 3
```
= 2 properties ✅

Use consistent, unique `listing_id` values.

---

## Temporal Rules

- Use real collection timestamps for `observed_at`
- Do NOT backdate `observed_at` to artificially extend temporal span
- Do NOT forward-date `observed_at` to fake freshness
- A 7-day span requires observations genuinely collected across ≥7 calendar days

---

## Privacy Rules

- Do NOT record owner/tenant names
- Do NOT record phone numbers
- Do NOT record national ID numbers (Aadhaar, PAN)
- `listing_id` must be a non-identifying code (e.g. `FIELD-VEL-001`, not the owner's name)
- `notes` are internal-only and never published to the UI
- `address_raw` may include street name and area, but NOT personal details
