## 1. Executive Summary

This audit is an exhaustive, ground-truth inspection of the RIVO repository. The codebase represents a cleanly architected foundation with working end-to-end integration between a FastAPI backend and a React 19 + Tailwind CSS v4 frontend. 

The previous developer successfully built:
1. Pure mathematical algorithm implementations for household affordability, transport burden, cash burden, and time tax, backed by **39 passing unit tests**.
2. An API contract with **12 passing integration tests** across rentals, routing, worker profiles, facilities, data source registries, and scenario evaluation.
3. A functional, aesthetically refined frontend with a 3-step search form, split-screen property list, interactive Leaflet map, multi-modal route comparison modal, and policy scenario simulator.

**However, virtually all operational data is currently simulated, fixture-based, or mocked:**
- **Rentals:** 90 listings in `rental_seed.json` generated by anchoring synthetic units to 45 real CMRL metro stations (`backend/scripts/generate_gtfs_anchored_rentals.py`). No live portal or scraper feeds are active.
- **Routing:** Real-time routing defaults to `MockRouteProvider`, which computes straight-line Haversine distance multiplied by an arbitrary route factor (1.3–1.5) divided by speed (`distance / assumed_speed`), because Google Routes API keys and local OpenTripPlanner (OTP) servers are not configured.
- **Family Facilities:** Neither seed files nor DB records exist for schools, hospitals, or pharmacies. In mock/local mode without Google Places API keys, facility proximity queries return empty results.
- **Rent Model (ML):** LightGBM/XGBoost is non-existent (`data/models/rent_model.joblib` does not exist); rental percentile predictions (`p25`, `p50`, `p75`) are completely null.
- **RIVO City (Planner Scenario Engine):** Computes before/after impact using static hardcoded multipliers (`new_stops * 150` reachable workers, `new_stops * 1.5` mins saved) rather than re-evaluating the transit network.
- **Database & Migrations:** Alembic has zero migration revisions in `backend/alembic/versions/`. SQLite fallback in `backend/app/db/session.py` attempts to import `aiosqlite`, which is omitted from `backend/requirements.txt`.

## 3. Implemented Features

- ✅ **RIVO Home 3-Step Search Interface:** Partitioned into `1. Workplace & Travel`, `2. Worker & Budget`, and `3. Family Layer` to prevent cognitive overload.
- ✅ **Dynamic Income & Ceiling Prefill:** Selecting worker occupations (Nurse, Teacher, Bus Driver, Delivery Rider, Construction Worker) auto-populates PLFS 2025 monthly median incomes and computes suggested 30% rent budgets.
- ✅ **Multi-Modal Route Comparison Card:** Computes and compares Transit (Metro/Bus), Two-Wheeler, Walking, and Car routes, assigning dynamic badges (`FASTEST`, `CHEAPEST`).
- ✅ **Transparent Data Freshness Badging:** Visual pill tags on every listing and route result indicating `LIVE`, `RECENT`, `PERIODIC`, or `ESTIMATED`.
- ✅ **Data-Driven Explainability Generator:** Rule-based explanation generation in `app/services/algorithms/affordability.py` generating `why_recommended` and `why_not_recommended` tags without opaque LLM hallucinations.
- ✅ **Pure Affordability Calculations:** Computes Housing Burden %, Transport Burden %, Cash Burden %, and Monthly Commute Hours (Time Tax).
- ✅ **Hard Constraints Filtering:** Enforces hard rejection of properties exceeding max rent, mismatched BHK, unavailable status, or commute exceeding max threshold.
- ✅ **Authoritative Data Sources Registry:** Full metadata registry exposing all 11 Chennai datasets with legal attribution and license terms at `/api/v1/data/sources`.
- ✅ **GTFS Seed Data Assets:** Full GTFS feeds stored in `data/seed/gtfs/` for CMRL Metro (stops, routes, frequencies, trips), MTC Bus (stops, routes, trips), and Unified Chennai GTFS.

## 8. Rental Pipeline Status

The pipeline in [`backend/app/services/recommendation_service.py`](file:///c:/Project/Hackathons/Sustain-a-thon/Code/backend/app/services/recommendation_service.py) executes in the following sequence:

```
1. Provider Fetch (MockRentalProvider reads rental_seed.json)
      ↓
2. Hard Filter (max_rent_monthly, bhk, property_type, availability)
      ↓
3. Spatial Filter (Haversine distance <= search_radius_km, default 18km)
      ↓
4. Finalist Truncation (Cap at _MAX_ROUTE_FINALISTS = 200 listings)
      ↓
5. Multimodal Route Evaluation (Best route per listing to workplace)
      ↓
6. Facility Access Query (Nearest School, Hospital, Pharmacy)
      ↓
7. Affordability & Burden Calculation (Housing %, Transport %, Cash %, Time Tax)
      ↓
8. Component Scoring (Housing 30%, Commute 25%, Transport 15%, Family 15%, Work 10%, Confidence 5%)
      ↓
9. Explainability Generation (Positive/negative reasons text)
      ↓
10. Sorting & Pagination (Rank by score_total descending)
```

**Evaluation:** The pipeline structure is architecturally sound and strictly enforces the non-negotiable rule: *do not route thousands of listings against every destination*. However, because the ML rent surface is missing, rent calibration is omitted.

## 9. Routing Pipeline Status

- **Real Multimodal Routing vs Formula:**
  - When `GOOGLE_ROUTES_API_KEY` is empty and OTP is offline, [`MockRouteProvider`](file:///c:/Project/Hackathons/Sustain-a-thon/Code/backend/app/services/providers/route_mock.py#L39-L70) executes.
  - It computes straight-line distance via Haversine and applies:
    - **Walk:** `speed = 4.5 km/h`, `route_factor = 1.4`
    - **Transit:** `speed = 22.0 km/h`, `route_factor = 1.5`, `fare = max(7, dist_km * 1.5)`
    - **Two-Wheeler:** `speed = 28.0 km/h`, `route_factor = 1.3`, `fuel = dist / 45 * 105`
    - **Drive (Car):** `speed = 22.0 km/h`, `route_factor = 1.35`, `fuel = dist / 14 * 105`
  - **Verdict:** The current fallback literally uses `distance / assumed_speed`. True transit network routing (transfers, schedules, waiting time) is currently simulated.

## 12. Affordability / Recommendation Logic

### Exact Formulas ([`affordability.py`](file:///c:/Project/Hackathons/Sustain-a-thon/Code/backend/app/services/algorithms/affordability.py)):
1. **Housing Burden:** $\text{rent} / \text{income}$
2. **Transport Burden:** $\text{monthly\_transport\_cost} / \text{income}$
3. **Cash Burden:** $(\text{rent} + \text{maintenance} + \text{transport}) / \text{income}$
4. **Time Tax (Monthly Commute Hours):** $\text{one\_way\_minutes} \times 2 \times \text{work\_days} / 60$
5. **Monthly Transit Cost:** $\text{one\_way\_fare} \times 2 \times \text{work\_days}$
6. **Monthly Fuel Cost:** $(\text{distance\_km} / \text{efficiency\_kmpl} \times \text{fuel\_price}) \times 2 \times \text{work\_days}$

### Scoring Weights:
- Housing Fit: **30%**
- Commute Fit: **25%**
- Transport Fit: **15%**
- Family Fit: **15%**
- Workplace Access: **10%** (neutral 0.5 default)
- Confidence: **5%**

## 15. Performance Risks

1. **Routing Finalist Cap:** The code enforces `_MAX_ROUTE_FINALISTS = 200`. If Google Routes API were active, 200 listings $\times$ 4 modes = 800 API requests per search if not cached, which would quickly exhaust quotas and create 3–8 second latencies.
2. **PostGIS Queries in Loop:** In `recommendation_service.py`, `_get_facility_access` runs 3 separate DB queries (`School`, `Hospital`, `Pharmacy`) for *each* of the 200 finalists sequentially, resulting in up to 600 database queries per search (N+1 query problem).
3. **Frontend Bundle Size:** Current Vite build bundle is 433 kB (128 kB gzipped). Clean and acceptable for an MVP.
